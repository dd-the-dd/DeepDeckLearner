Le SDK est aussi votre connexion à notre service League. Le même agent peut jouer sur un moteur local ou se connecter à DeepDeck League avec votre compte et ses accès autorisés. Le SDK reste public ; il ne contourne pas les permissions du serveur.

Un tour de jeu, en cinq étapes

Comment une carte devient une action.

  1. 01 · LIRETexte Oracle

    La description officielle de la carte sert de matière première.

  2. 02 · COMPRENDREParser → règles

    Le texte est traduit en capacités et effets structurés que l’Engine sait exploiter.

  3. 03 · PROPOSEREngine → choix légaux

    L’état courant détermine ce que le joueur ou son IA peut faire.

  4. 04 · CHOISIRHumain ou agent

    Vous cliquez dans Pixi, ou l’agent répond via le SDK après évaluation de sa stratégie.

  5. 05 · RÉSOUDREEngine → Pixi

    L’Engine vérifie et applique l’action ; Pixi affiche le nouvel état. Puis la boucle continue.

Lire une carte n’est pas encore la jouer correctement. Un parser peut reconnaître une capacité alors que son exécution nécessite encore un correctif. Le schéma explique les responsabilités ; il ne promet pas que toutes les cartes de Magic sont déjà parfaitement prises en charge.

Qui fait quoi ?

Six rôles, faciles à distinguer.

Comme dans un club de jeu : un lieu de rencontre, un atelier, un arbitre, un lecteur de règles, une table et une connexion standard pour les agents.

01Plateforme privée

Le site web

Le club et son organisateur.

DeepDeck League réunit les comptes, la recherche et la création de decks, la synchronisation, les rencontres et leurs résultats. Son API vérifie l’identité, les permissions et les limites d’utilisation.

Ce qui n’est pas son rôle

Le navigateur n’accorde pas lui-même un niveau Patreon et ne remplace pas l’arbitre de jeu. Un agent peut tourner chez son propriétaire tout en participant à une rencontre du serveur.

Site : deepdeckleague.com
Dépôt de la plateforme : privé, mtg-oracle-engine.
02Code public · MIT

L’Engine

L’arbitre et la mécanique du jeu.

DeepDeckEngine conserve l’état de la partie, calcule les actions légales et applique les changements : payer un coût, choisir une cible, résoudre un effet, gérer le combat et les marqueurs.

La limite importante

Il fait autorité sur les règles, pas sur la meilleure stratégie. Il peut autoriser une attaque très mauvaise ou un contre sur son propre sort : c’est à l’agent de bien choisir parmi les options légales.

Source : DeepDeckEngine
03Dans l’Engine · MIT

Le parser

Le traducteur des cartes.

Il transforme le texte Oracle en une représentation structurée des capacités, coûts, conditions et effets. Ces structures servent ensuite à la logique de jeu.

Pourquoi le séparer dans le schéma ?

C’est une responsabilité différente de l’exécution, mais le parser canonique fait partie du dépôt Engine. Ce n’est ni un LLM qui improvise les règles à chaque tour, ni un service cloud indépendant obligatoire.

Source et licence : DeepDeckEngine
04Code public · MIT

DeepDeck Learner

Votre atelier personnel.

L’application locale sert à préparer des decks et agents, personnaliser leurs stratégies, jouer contre eux, lancer des lots de matchs, consulter les statistiques et gérer les replays.

Pourquoi « Learner » sans entraînement obligatoire ?

L’agent programmatique utilise notamment un graphe de décisions pondéré. L’assistant LLM peut aider à personnaliser ce travail ; cela n’exige pas un entraînement GPU et ne transforme pas chaque décision de jeu en appel LLM.

Source : DeepDeckLearner
05Code public · MIT

DeepDeck Pixi

La table que vous regardez et touchez.

Le rendu visuel présente les cartes, la main, la vie, les cibles, les animations et les sons. Il peut afficher une partie en cours ou parcourir les états enregistrés d’un replay.

Ce qu’une image ne décide pas

Pixi affiche la vue que la session lui transmet. Il ne doit pas inventer des informations cachées ni décider qu’une action est légale. Les perspectives de spectateur dépendent des données et permissions disponibles.

Source : DeepDeckPixi
06Code public · MIT

L’Agent SDK

La prise standard de votre IA.

DeepDeckAgent fournit le protocole et les outils Python pour connecter un agent au moteur : recevoir les observations et demandes de décision, puis envoyer une réponse dans le format attendu.

SDK, agent et LLM : trois choses différentes

Le SDK est la connexion. Votre agent est la stratégie. Un LLM est un assistant facultatif pour l’éditer. Le SDK n’oblige ni à un fournisseur LLM ni à une stratégie particulière et n’accorde pas, à lui seul, l’accès à un compte League.

Source : DeepDeckAgent

La frontière à ne pas confondre

Code ouvert ≠ données ouvertes.

« Public » décrit ici le dépôt de code. La visibilité d’un deck, d’un profil ou d’une partie est une autre décision, liée à l’utilisation et aux règles de publication.

Les briques publiques

Ce que l’on peut étudier et réutiliser

  • Engine et parser Oracle.
  • Affichage Pixi.
  • Application Learner et modèles programmatiques partagés.
  • Agent SDK Python.

Dépôts publics sous MIT vérifiés sur GitHub. Des modifications locales non publiées ne sont pas automatiquement présentes dans leur version publique.

La plateforme privée

Ce qui n’est pas distribué avec ces dépôts

  • Le code du site et des services League dans le dépôt privé.
  • Les bases de comptes et données hébergées.
  • Les secrets serveur, droits et configurations de production.
  • Les poids de modèles privés, le cas échéant.

Un fichier MIT dans un dépôt privé ne le rend pas accessible au public. Les pages publiques du site ne rendent pas son backend open source.

Votre espace personnel

Ce qui ne doit pas finir dans Git

  • Les agents personnalisés et leurs configurations locales.
  • Le profil .deepdeck/ : decks de travail, base locale, statistiques et replays.
  • Clés API et connexions personnelles aux fournisseurs LLM.
  • Fichiers d’environnement, checkpoints et sauvegardes privées.

« Ignoré par Git » n’est pas un chiffrement. Synchroniser un deck, participer à la League ou demander l’aide d’un fournisseur LLM peut transmettre les données nécessaires à ce service.

Et les cartes Magic ? La licence MIT des logiciels ne couvre pas automatiquement les illustrations, logos, marques ou textes des cartes. Leurs droits et conditions d’utilisation restent distincts.

Trois parcours concrets

À quoi tout cela sert pour le joueur ?

Je teste mon deck.

  1. Je choisis mon deck et un adversaire dans le Learner.
  2. Les agents se connectent par le SDK à l’Engine local.
  3. Pixi affiche la partie ; le Learner conserve les résultats et replays selon mes réglages.
Pas besoin de League ni de LLM pour jouer localement.

J’envoie mon IA en League.

  1. Je connecte mon compte et prépare les decks autorisés.
  2. La plateforme vérifie mes accès et organise la rencontre.
  3. L’agent joue via le SDK ; les résultats sont traités par la League.
Le compte et les limites viennent du serveur, pas du code local.

Je personnalise en discutant.

  1. Je configure un fournisseur LLM compatible.
  2. Le chat utilise des outils autorisés pour chercher des cartes ou modifier un deck et une stratégie.
  3. L’agent programmatique joue ensuite avec sa configuration, sans devoir consulter le chat à chaque tour.
Le LLM aide à construire l’agent ; il n’est pas l’arbitre du jeu.

Les questions qui reviennent.

Un agent doit-il forcément être public ?

Non. Les outils et les modèles partagés peuvent être publics, tandis que votre agent personnalisé reste dans votre espace local non versionné. L’inscrire à la League ne signifie pas, à lui seul, publier son code.

Pourquoi avoir un site et une application ?

Le site est l’espace partagé pour les comptes, decks et rencontres. L’application est l’espace personnel pour expérimenter, exécuter des agents et gérer les fichiers locaux. Ils utilisent des briques communes sans être le même produit.

Le LLM voit-il toutes mes parties ?

Il n’est pas automatiquement dans la boucle des décisions de jeu. Ce qui lui est transmis dépend du chat, de ses outils et du fournisseur configuré. Ne lui envoyez pas de secrets inutiles ; une clé personnelle n’est jamais une donnée à publier.

Ce schéma décrit-il des fonctions déjà déployées ?

Il décrit les responsabilités et la séparation des dépôts vérifiées dans le projet. Il ne certifie pas qu’une modification locale ou qu’une future compétition avec achievements est déjà en production.
